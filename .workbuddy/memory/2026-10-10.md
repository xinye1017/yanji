## 一、当前真实架构（高优先级记忆）

- **Yanji 2.0 = Android Add-to-App（React Native UI + Kotlin 原生业务）**，不是以往的纯 Jetpack Compose 前端。当前主 UI 事实源为 `App.tsx`、`src/screens/**`、`src/navigation/**`、`src/components/**`。
- 前端 `package.json`：React Native 0.87.1、React 19.2.3、TypeScript 5.8.x；主要依赖 Reanimated 4、Worklets、SVG、Safe Area Context、`react-native-blur-overlay`。主题语义 Token 在 `src/theme/tokens.ts`，由 `ThemeProvider.tsx` 提供；玻璃底栏参数在 `src/theme/liquidGlass.ts`。
- 宿主在 `app/src/main/java/com/example/yanji/YanjiApplication.kt` / `MainActivity.kt`，使用 Hermes、新架构、Bridgeless、Fabric；手工注册 ReactPackage/原生库，不能仅凭 npm install 判断原生组件完成接入。
- 业务与持久化仍为 Kotlin：`data/YanjiRepository.kt`、`data/StudyStatisticsRepository.kt`、`data/timer/**`、`service/FocusTimerService.kt`、`data/db/YanjiDatabase.kt`。**Room 是唯一真实业务持久化源**，不存在“前端另一份计时事实/数据库”。
- 数据库以 `YanjiDatabase.kt` 为准：**`@Database(version = 22)`**，注册 v1→v22 显式迁移，未启用破坏性迁移回退；Entity/迁移变化需同步检查 `app/schemas/**`。README/旧项目记忆中更低的版本号均已过时。
- Kotlin ↔ JS 通过 `app/src/main/java/com/example/yanji/bridge/YanjiTimerModule.kt`、`YanjiDataModule.kt`、`YanjiThemeModule.kt` 与 `src/bridge/index.ts` 交互。双边契约要一起变更；相关 Node 检查在 `test-e2e/contracts/**`。
- 专注：`TimerMachine` / `ActiveSessionCoordinator` / `FocusTimerService` 持有真实计时，用 `SystemClock.elapsedRealtime`；前端只渲染原生 tick/state 事件，不在 React 中另建权威计时器。活动快照在 noBackupFilesDir 用于恢复；通知的 Chronometer 自行计时，不得每秒重发 notify。
- 安全：API Key 仅走原生 Keystore + 非备份目录，异常时 fail-closed；禁止打印、提交或透传到前端持久化。
- 当前构建：`npm run typecheck`、`npm test`（Node 合同/静态/逻辑测试）、`npm run bundle:android`、`./gradlew.bat assembleDebug`（Windows 环境）。**RN JS 变更必须先重新生成 `app/src/main/assets/index.android.bundle`，再打 APK**；单跑 Gradle 不保证拿到新 UI。不要混淆不同层面的测试通过。

## 二、当前前端产品面（不能和旧 Compose 产品功能混同）

- `App.tsx`：三大主屏常驻 mounted，非活动页通过 opacity/pointer events/无障碍隔离以保留局部状态；弹层置于其上；Android 返回优先关闭弹层。
- 导航仅 `Today`「今天」、`Focus`「专注」、`Review`「回顾」，设置从“今天”页进入；见 `NavigationShell.tsx` 与 `BottomTabBar.tsx`。玻璃浮动底栏使用 blur-overlay + Reanimated 弹簧胶囊。
- `TodayScreen.tsx`：真实今日统计/考研倒计时、单个适应状态的 CTA、待办/任务、记录此刻入口。
- `FocusScreen.tsx`：科目选择、COUNTDOWN / STOPWATCH、倒计时快捷值 25/45/60/90 与 5~180 分钟 Stepper；默认 COUNTDOWN。正在计时时支持暂停、继续、完成、放弃和随时记一笔；任务可带 subject / planned minutes / taskId。
- `ReviewScreen.tsx`：按日期的时间线、单日/自然周/自然月统计、科目分布与趋势、记录编辑与删除。
- `RecordMomentModal.tsx`：轻量纯文本记录，保存到原生 Room，可关联当前会话；不应打断计时。当前 RN Settings 只包含有限的主题和备考信息，不等同于旧 Compose 的 AI、成就、模考、全功能随笔编辑器等界面。**这些 Kotlin 原生能力/历史代码存在，不代表当前 RN 入口已对用户暴露。**

## 三、代码审查结果与优先排查项（未动态复现）

1. **P1 文档/门禁事实冲突**：`README.md` 顶部 `project-facts` 声明 `roomSchema=21`，而实际 `YanjiDatabase.kt` 为 22。CI 的 `scripts/check-project-facts.sh` 会核对该字段，静态对照显示存在门禁失败风险。修复时应更新 README 声明以及文档内相互矛盾的 Room 版本描述，不得反向降低 Schema。
2. **P1 项目记忆过期**：`.workbuddy/memory/MEMORY.md` 仍写“单 module Kotlin + Compose”、Room v15 和 Compose 唯一主题事实源；`PROJECT.md` 顶部 Room v20 与 README v21 同样落后。Agent 后续应首先读 `AGENTS.md` 与真实运行代码，不要套用旧 Compose UI 的组件、路径或设计限制。
3. **P2 跨午夜日期**：`TodayScreen.tsx` 与 `FocusScreen.tsx` 用 `const [date] = useState(todayIso)` 只计算初始日期，且三页常驻 mounted；长时间不退出 App 跨午夜时，数据请求或“记录此刻”的日期可能仍指向前一天。建议用 AppState/日期变更策略验证并修复，同时加入跨日用例。
4. **P2 用户可见的失败反馈**：多个 RN 页面在 Bridge 读写失败时仅 `catch { }` 或保留旧快照；虽然避免伪造成功，但可能让任务切换、删除或数据加载失败无明确反馈。建议区分“读取失败/正在加载/空数据/操作失败”，保留安全恢复机制并补充用户反馈。
5. **P2 CI JS 验证覆盖核查**：`.github/workflows/android-quality.yml` 当前明确有项目事实、数据 fixture、设计 Token、原生 JVM 测试、lint、debug/release 构建和 API 34 插桩；在已读 workflow 的构建步骤里未见显式 `npm run typecheck` / `npm test` / `npm run bundle:android`。需要确认 RN 静态检查与离线 bundle 刷新是否已由其他入口执行，避免“编译通过、实际旧 JS”。
6. **P3 长期维护**：RN 页面与 UI 组件个别文件较大（如 `ReviewScreen.tsx` 970 行、`TodayScreen.tsx` 652 行、`YanjiUI.tsx` 较长）；未来做复杂 UI 迭代时宜按交互单元抽离 hook / 子组件并加强针对性测试，暂不做为了拆分而拆分。
7. **测试状态**：Codex 当前 workspace 无最近执行记录；**以上任何风险都不是本轮测试失败的断言，本轮未执行测试**。仓库虽有 `test-e2e/` 四层 Node 测试与 Kotlin 测试，但“有测试代码”不等于“在此快照已通过”。
