# 提示词

你现在是一名负责长期维护 Android/Kotlin/Jetpack Compose 项目的高级工程师。请对当前仓库“研迹 Yanji”进行一次严格的全仓代码审计。

这是一个个人自用的考研学习 App，所有历史代码均由 AI 生成，因此不要默认现有实现、注释、README 或架构决策一定正确。必须以实际源码、Gradle 配置、Room schema、Manifest、测试代码为准进行验证。

本轮任务只做审计和报告，不要大规模修改代码。

核心目标按优先级排列：

P0：

1. 数据丢失风险
2. Room schema / migration 正确性
3. fallbackToDestructiveMigration 风险
4. 导入导出与备份缺失
5. API Key 与敏感信息存储
6. Android Auto Backup / dataExtractionRules 是否可能包含敏感数据
7. FocusTimerService 的计时正确性
8. 进程死亡 / Service 重启 / Activity 重建后的 active timer 状态
9. 重复 finish 导致重复数据的可能性
10. 初始化 seed 是否可能在用户主动清空数据后重新出现

P1：

1. YanjiRepository 是否承担过多职责
2. object singleton 对测试性的影响
3. Room + 内存 MutableStateFlow 双状态源造成的一致性问题
4. Compose 是否直接读取 Repository / DAO
5. 是否缺少 ViewModel / UiState
6. HomeScreen / FocusScreen / ExamScreen 等大型文件中可拆出的业务与 UI
7. Navigation3 与自定义 screenStack 并存的问题
8. 未使用模板代码、死代码、重复代码
9. Coroutine scope、Dispatcher、异常处理、取消传播
10. Flow 是否使用 collectAsStateWithLifecycle
11. 是否存在重复 collect / 永不取消的协程
12. Compose recomposition 热点

P2：

1. 数据模型中以中文显示文本作为业务值的问题
2. String mode/status/type 是否应该改为稳定 enum/ID
3. Journal tags CSV 存储问题
4. Room Index / ForeignKey / cascade 是否完整
5. 时间字段与 LocalDate/Instant/epoch 的使用是否一致
6. 跨午夜、修改系统时间、修改时区对统计与 timer 的影响
7. 统计口径是否在多个页面重复实现
8. Achievement 解锁是否幂等
9. QuickStart 排序与删除是否存在竞态
10. 聊天消息/session 删除是否存在孤儿记录

AI 模块：

1. HttpURLConnection 使用是否安全、可取消、正确关闭资源
2. 是否配置 connect/read timeout
3. HTTP 401/403/404/429/5xx 是否被错误地统一吞掉
4. API 失败后静默本地 fallback 是否导致 UI 误导
5. API Key 是否可能出现在 Log、异常、备份或 prompt
6. Base URL 是否允许不安全 HTTP
7. org.json 手工解析的脆弱点
8. OpenAI-compatible 响应字段兼容性
9. model list 拉取失败行为
10. AI Diagnostic JSON parser 的容错与 schema
11. prompt injection 数据隔离是否仅依赖提示词
12. journal/raw text 是否发送过多
13. chat context 是否仅机械截取最近 8 条
14. AI 自动标题是否可能覆盖用户手动标题
15. “一键加计划”和“保存到日记”是否可能重复执行

FocusTimerService：
请逐条分析：

- stopwatch
- countdown
- pause
- resume
- finish
- cancel
- notification actions
- Activity action
- lock screen
- background
- device deep sleep
- process death
- Service restart
- Task removal
- system clock change
- timezone change
- repeated STOP
- countdown reaching zero
- notification permission denied

确认 interval timing 是否基于 SystemClock.elapsedRealtime，而不是通过 delay(1000) 累加或 System.currentTimeMillis 直接计算。

数据库：
列出每张 Entity：

- primary key
- unique constraint
- index
- foreign key
- cascade
- nullable
- default
- domain mapping
- possible invariant

并检查所有 DAO：

- 是否存在 N+1
- 是否错误加载整表
- Flow query 是否合理
- 是否缺失 transaction
- 排序是否稳定
- delete/update 是否幂等

测试：
生成“缺失测试矩阵”，重点覆盖：

- migration 1→最新
- backup round-trip
- timer state machine
- statistics
- date boundary
- active timer restoration
- import rollback
- achievement
- AI parser
- AI fallback
- ViewModel
- Compose critical path

最终输出：

1. Executive Summary
2. P0 Critical Findings
3. P1 High Priority Findings
4. P2 Maintainability Findings
5. Data Model Audit
6. Timer Audit
7. AI Audit
8. Compose/UI Architecture Audit
9. Navigation Audit
10. Test Gap Matrix
11. Dead Code / Duplicate Code
12. Recommended Target Architecture
13. Recommended Refactor Order
14. 每一项建议标明：

- 文件
- 类/函数
- 风险
- 修改建议
- 修改复杂度 S/M/L
- 是否需要 DB migration
- 必须新增哪些测试

重要规则：

- 不要因为代码“现在能跑”就认为没有问题。
- 不要为了套 Clean Architecture 而过度抽象。
- 不要建议微服务、云后端或账号系统。
- 不要进行无意义格式化。
- 不要把所有问题一次重写。
- 对不能从代码确定的事情明确写“未验证”。
- 必须实际运行可运行的 Gradle tests / lint / build，并报告结果。
- 如果现有测试失败，区分“修改前已经失败”和“本次导致失败”。
